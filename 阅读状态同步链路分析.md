# 用户阅读状态同步链路分析

## 一、整体架构概览

用户阅读状态（已读/已见/归档等）的同步是一个跨多终端、多服务的完整链路。系统采用 **"HTTP上报 + WebSocket广播 + 数据库持久化 + 最终一致性补齐"** 的架构模式。

#### 1.1 状态上报机制 (`src/notifications/helpers.ts`)

**核心逻辑：乐观更新 + 事件驱动**

```typescript
// 单个通知标记为已读
export const read = async ({ emitter, apiService, args }) => {
  // 1. 生成乐观更新值
  const optimisticValue = new Notification({ ...notification, isRead: true, readAt: now });
  
  // 2. 发射 pending 事件，UI 立即响应
  emitter.emit('notification.read.pending', { data: optimisticValue });
  
  try {
    // 3. 异步调用后端 API
    const response = await apiService.read(notificationId);
    
    // 4. 发射 resolved 事件，更新最终状态
    emitter.emit('notification.read.resolved', { data: updatedNotification });
  } catch (error) {
    // 5. 失败时回滚
    emitter.emit('notification.read.resolved', { error });
  }
};
```

**上报 API 接口：**

| 操作 | HTTP 方法 | 路径 | 说明 |
|------|----------|------|------|
| 标记单个已读 | PATCH | `/inbox/notifications/:id/read` | 单个通知 |
| 标记单个未读 | PATCH | `/inbox/notifications/:id/unread` | 单个通知 |
| 批量标记已见 | POST | `/inbox/notifications/seen` | 支持按 ID 或筛选条件 |
| 批量标记已读 | POST | `/inbox/notifications/read` | 支持按标签/数据筛选 |
| 批量归档 | POST | `/inbox/notifications/archive` | 支持按条件批量 |

#### 1.2 WebSocket 实时监听 (`src/ws/socket.ts`)

**连接管理：**
- 使用 `socket.io-client` 建立长连接
- 自动重连：`reconnectionDelayMax: 10000`
- 认证方式：URL Query 参数携带 JWT Token

**监听的实时事件：**

| 事件名 | 触发时机 | 数据结构 |
|--------|----------|----------|
| `notification_received` | 收到新通知 | `{ message: InboxNotification }` |
| `unseen_count_changed` | 未见计数变化 | `{ unseenCount: number, hasMore: boolean }` |
| `unread_count_changed` | 未读计数变化 | `{ unreadCount: number, counts: { total, severity }, hasMore }` |

#### 1.3 本地缓存与事件同步 (`src/cache/notifications-cache.ts`)

**缓存键设计：**
- 基于查询参数（tags、read、archived、severity 等）生成 JSON 字符串作为键
- 自动监听状态变更事件，更新缓存中的通知状态

##### 2.2.1 标记通知为已见 (`mark-notifications-as-seen.usecase.ts:1-280`)

**执行流程：**
1. 校验订阅者存在性
2. 按 ID 或筛选条件批量更新数据库

**关键代码片段：**

```typescript
async execute(command: MarkNotificationsAsSeenCommand): Promise<void> {
  // 1. 批量更新数据库（分批处理，每批50条）
  const BATCH_SIZE = 50;
  for (const idChunk of notificationIdChunks) {
    const batchResults = await this.messageRepository.updateMessagesStatusByIds({
      environmentId, subscriberId, ids: idChunk, seen: true,
    });
    updatedMessages.push(...batchResults);

    data: {
      event: WebSocketEventEnum.UNSEEN,
      userId: subscriber._id,
      _environmentId,
      contextKeys,
    },
    groupId: subscriber._organizationId,
  });
}
```

#### 3.2 核心更新方法

##### `updateMessagesStatusByIds` (第751行)

按通知 ID 列表批量更新状态：

```typescript
async updateMessagesStatusByIds({
  environmentId, subscriberId, ids, seen, read, archived, snoozedUntil, contextKeys
}): Promise<MessageEntity[]> {
  const query = {
    _environmentId: environmentId,
    _subscriberId: subscriberId,
    _id: { $in: ids.map(id => new Types.ObjectId(id)) },
    ...(contextKeys?.length && { contextKeys: { $in: contextKeys } }),
  };
  
  return this.updateMessagesStatus({ query, seen, read, archived, snoozedUntil });
}
```

##### `updateMessagesFromToStatus` (第790行)

按筛选条件批量更新：

```typescript
async updateMessagesFromToStatus({
  environmentId, subscriberId, from, to, contextKeys
}): Promise<MessageEntity[]> {
  // from: 筛选条件（tags, data, seen, read, archived）
  // to: 目标状态
  let query = {
    _environmentId, _subscriberId,
    ...(contextKeys?.length && { contextKeys: { $in: contextKeys } }),
    ...from.tagGroups && buildTagsQuery(from.tagGroups),
    ...from.data && getFlatObject({ data: from.data }),
  };
  
  return this.updateMessagesStatus({ query, ...to });
}
```

### 4. WebSocket 服务层 (`apps/ws`)

#### 4.1 网关层 (`socket/ws.gateway.ts:1-379`)

**核心职责：**
- 管理 WebSocket 连接生命周期
- 处理连接认证（JWT 校验）
- 按订阅者分组（Socket.IO rooms）
- 向在线客户端推送实时事件

**连接建立流程：**
```
客户端连接
    ↓
extractToken() - 从 handshake 提取 token
    ↓
getSubscriber() - JWT 校验，确认身份
    ↓
connection.join(subscriber._id) - 加入订阅者房间
    ↓
subscriberOnlineService.handleConnection() - 更新在线状态
```

**上下文隔离机制：**
每个连接携带 `contextKeys`，广播时进行精确匹配，确保多上下文场景下的数据隔离。

```typescript
private isExactMatch(messageContextKeys: string[], inboxContextKeys: string[]): boolean {
  if (messageContextKeys.length === 0) return inboxContextKeys.length === 0;
  if (messageContextKeys.length !== inboxContextKeys.length) return false;
  return messageContextKeys.every(key => inboxContextKeys.includes(key));
}
```

#### 4.2 事件路由 (`usecases/external-services-route/external-services-route.usecase.ts:1-157`)

根据事件类型执行不同的广播逻辑：

| 事件类型 | 处理逻辑 |
|----------|----------|
| `RECEIVED` | 推送完整通知内容 + 同步更新 unseen/unread 计数 |
| `UNSEEN` | 重新查询数据库，推送最新未见计数 |
| `UNREAD` | 重新查询数据库，推送最新未读计数（含严重程度分组） |

#### 4.3 在线状态管理 (`shared/subscriber-online/subscriber-online.service.ts:1-39`)

维护订阅者的在线状态：
```typescript
async handleConnection(subscriber) {
```

```typescript
private getWorkerProcessor() {
  return async (job) => {
    const data: IWebSocketDataDto = job.data;
    
    await this.externalServicesRoute.execute(
      ExternalServicesRouteCommand.create({
        userId: data.userId,
        event: data.event,
        payload: data.payload,

      })
```

**重要设计决策：**
> WS 任务采用 **at-most-once** 语义，失败不重试。因为 WS 消息是实时 UI 提示，过期后重播反而有害。客户端可通过主动拉取来修复状态。

## 四、关键设计决策与技术要点

### 1. 状态模型设计

**Seen vs Read 的区别：**
- **Seen（已见）**：通知出现在用户视野中，自动标记
- **Read（已读）**：用户主动点击查看，需要显式操作

**状态联动规则：**
- 标记为已读 → 自动标记为已见
- 标记为已归档 → 自动标记为已读+已见
- 标记为未见 → 自动取消已读+已归档

### 2. 多终端同步策略

**最终一致性保障：**
1. **实时通道**：WebSocket 推送计数变更事件（秒级）
2. **数据库基准**：HTTP API 拉取确保数据准确（用户主动刷新时）
3. **缓存失效**：状态变更后立即失效服务端缓存
4. **幂等操作**：重复标记同一状态不会产生副作用

### 3. 断线重连补齐机制

系统 **没有** 采用"事件溯源 + 离线消息队列"的复杂方案，而是采用更简洁的最终一致性策略：

1. **WebSocket 自动重连**：socket.io 内置重连机制，指数退避
2. **重连后主动拉取**：应用层监听 `connect` 事件，触发全量数据刷新
3. **计数基准对齐**：每次 WebSocket 推送的是数据库实时查询结果，不是增量事件
4. **本地缓存自愈**：客户端缓存监听所有状态事件，自动合并更新

**设计考量：**
- 避免维护复杂的离线消息队列和 ack 机制
- 计数推送是幂等的，重复推送不影响正确性
- 用户感知不到短暂的不一致（秒级内自愈）

### 4. Context Keys 隔离机制

支持同一订阅者在不同上下文（如不同租户、不同项目）下的状态隔离：
- 连接时携带 `contextKeys`
- 状态更新时指定 `contextKeys` 筛选条件
- WebSocket 广播时进行精确匹配
- 数据库查询时加入 `contextKeys` 过滤

### 5. 性能优化点

| 优化手段 | 实现位置 | 效果 |
|---------|----------|------|
| 批量更新分批处理 | `message.repository.ts` | 避免单次更新过多文档 |
| 乐观更新 | `packages/js/src/notifications/helpers.ts` | UI 无延迟响应 |
| 本地缓存 | `notifications-cache.ts` | 减少重复网络请求 |
| 服务端缓存 | `invalidate-cache.service.ts` | 加速计数查询 |
| 异步广播 | `web-sockets-queue.service.ts` | 解耦 HTTP 请求与 WS 推送 |
| 上下文匹配 | `ws.gateway.ts` | 避免不必要的消息发送 |
| 计数分页指示 | `getCount()` | 超过100条时返回 hasMore，避免全表扫描 |

## 七、断线恢复机制深度解析

### 7.1 `socket.connect.resolved` 事件触发链路

#### 7.1.1 事件发射源

**事件由两个 Socket 实现类各自独立发射：**

**1. Socket.IO 客户端 (`packages/js/src/ws/socket.ts:191-197`)**
```typescript
// 代码证据: socket.ts 第180-196行
this.#socketIo = io(this.#socketUrl, {
  reconnectionDelayMax: 10000,  // socket.io 内置自动重连
  transports: ['websocket'],
  query: { token: `${this.#token}` },
  ...(this.#socketOptions ?? {}),
});

this.#socketIo.on('connect', () => {
  this.#emitter.emit('socket.connect.resolved', { args });  // 连接成功
});

this.#socketIo.on('connect_error', (error) => {
  this.#emitter.emit('socket.connect.resolved', { args, error });  // 连接失败
});
```
> **证据**：`packages/js/src/ws/socket.ts:180-196`
> - Socket.IO 客户端依赖 `socket.io-client` 库内置的自动重连机制
> - 重连延迟策略：指数退避，最大延迟 10000ms
> - 无论是首次连接还是重连成功，都会触发 `socket.connect.resolved` 事件

**2. PartySocket 客户端 (`packages/js/src/ws/party-socket.ts:268-275`)**
```typescript
// 代码证据: party-socket.ts 第259-274行
const args = { socketUrl: this.#socketUrl };
this.#emitter.emit('socket.connect.pending', { args });

// ...

socket.addEventListener('open', () => {
  this.#startHibernationHeartbeat();
  this.#emitter.emit('socket.connect.resolved', { args });  // 连接成功
});

socket.addEventListener('error', (error) => {
  this.#emitter.emit('socket.connect.resolved', { args, error });  // 连接失败
});
```
> **证据**：`packages/js/src/ws/party-socket.ts:259-274`
> - PartySocket 基于 `partysocket` 库（Cloudflare WebSocket 客户端）
> - 同样支持自动重连，但事件监听方式为标准 `addEventListener`
> - 额外包含休眠心跳机制（每 25s 发送 ping）

#### 7.2.1 触发条件差异（何时使用哪个实现）

> **证据**：`packages/js/src/ws/socket-factory.ts:9-43`

| 部署类型 | 默认 Socket 实现 | 触发条件 |
|---------|----------------|----------|
| **Novu Cloud** | PartySocket | URL 匹配 `PARTY_SOCKET_URLS` 列表 |
| **自托管 (Self-hosted)** | Socket.IO | URL 不在列表中，或显式指定 `socketType: 'self-hosted'` |

#### 7.2.2 行为差异对比表

| 特性 | `socket.ts` (Socket.IO) | `party-socket.ts` (PartySocket) |
|------|------------------------|--------------------------------|
| **底层库** | `socket.io-client` | `partysocket` (Cloudflare) |
| **自动重连** | ✅ 内置（指数退避，最大10s） | ✅ 内置 |
| **心跳机制** | ❌ 依赖协议层 ping | ✅ **应用层心跳**（每25s发送ping） |
| **休眠检测** | ❌ | ✅ `HIBERNATION_HEARTBEAT_MS = 25000` |
| **认证方式** | Query 参数 `?token=xxx` | Query 参数 `?token=xxx` |
| **事件发射** | `socket.connect.resolved` | `socket.connect.resolved` |
| **消息协议** | Socket.IO 二进制协议 | 标准 WebSocket + JSON |
| **生产URL** | `https://ws.novu.co` | `wss://socket.novu.co` |
| **连接关闭清理** | 简单 disconnect | ✅ 清理心跳定时器 |

**PartySocket 休眠心跳实现 (`party-socket.ts:228-251`)：**
```typescript
// 代码证据: party-socket.ts 第228-251行
#startHibernationHeartbeat(): void {
  this.#clearHibernationHeartbeat();
  this.#hibernationHeartbeatIntervalId = setInterval(() => {
    const socket = this.#partySocket;
    if (!socket || socket.readyState !== WebSocket.OPEN) {
      return;
    }
    try {
      socket.send(HIBERNATION_PING_PAYLOAD);  // 'ping'
    } catch {
      // Socket may have closed between readyState check and send
    }
  }, HIBERNATION_HEARTBEAT_MS);  // 25,000ms
}
```
> **证据**：`packages/js/src/ws/party-socket.ts:228-251`
> - 设计目的：防止移动设备/浏览器休眠导致 WebSocket 连接被回收
> - 每 25 秒发送一次 ping 消息保持连接活跃

## 十一、浏览器多标签页环境下的连接管理

### 11.1 核心问题与设计目标

**问题场景：**
用户在同一浏览器打开多个标签页访问同一应用，每个标签页都尝试建立独立的 WebSocket 连接，导致：
- 连接资源浪费（N 倍连接数）
- 重复事件处理
- 服务端连接压力倍增

**设计目标：**
- 单用户单浏览器 **仅保持一个** 活跃 WebSocket 连接
- 所有标签页都能实时接收状态更新
- 标签页关闭/切换时自动接管连接
- 对上层应用透明

---

### 11.3 useWebSocketEvent Hook 完整解析

```typescript
// 代码证据: useWebsocketEvent.ts 第1-46行
export const useWebSocketEvent = <E extends SocketEventNames>({
  event: webSocketEvent,
  eventHandler: onMessage,
  enabled = true,
}: {
  event: E;
  eventHandler: (args: Events[E]) => void;
  enabled?: boolean;
}) => {
  const novu = useNovu();
  // 通道名称 = 应用ID + 订阅者ID + 上下文Key + 事件类型
  const channelName = `nv_ws_connection:a=${novu.applicationIdentifier}:s=${novu.subscriberId}:c=${novu.contextKey}:e=${webSocketEvent}`;

  // 1. 创建 BroadcastChannel 用于标签页间通信
  const { postMessage } = useBrowserTabsChannel({
    channelName,
    onMessage,
    enabled,
  });

  // 2. 事件处理器：既处理本地事件，也广播给其他标签页
  const updateReadCount: EventHandler<Events[E]> = (data) => {
    onMessage(data);           // 本地处理
    postMessage(data);         // 广播给其他标签页
  };

  useEffect(() => {
    if (!enabled) return;

    let cleanup: () => void;
    // 3. 请求 Web Lock：只有一个标签页能获得锁
    const resolveLock = requestLock(channelName, () => {
      // 4. 获得锁的标签页才真正订阅 Novu WebSocket 事件
      cleanup = novu.on(webSocketEvent, updateReadCount);
    });

    return () => {
      if (cleanup) {
        cleanup();
      }
      resolveLock();  // 释放锁，允许其他标签页接管
    };
  }, [enabled]);
};
```

### 11.4 两大核心组件的角色分工

#### 11.4.1 Web Locks API：首领选举

**实现代码：`packages/react/src/utils/requestLock.ts:1-29`**

```typescript
// 代码证据: requestLock.ts 第1-29行
export function requestLock(id: string, cb: (id: string) => void) {
  // 降级处理：不支持 Lock API 则直接执行
  if (!('locks' in navigator)) {
    cb(id);
    return () => {};
  }

  let isFulfilled = false;
  let promiseResolve: () => void;
  const promise = new Promise<void>((resolve) => {
    promiseResolve = resolve;
  });

  // 请求命名锁，浏览器保证同一时间只有一个标签页获得
  navigator.locks.request(id, () => {
    if (!isFulfilled) {
      cb(id);  // 获得锁后执行回调（订阅 WebSocket 事件）
    }
    return promise;  // 保持锁直到组件卸载
  });

  // 返回释放锁函数
  return () => {
    isFulfilled = true;
    promiseResolve();
  };
}
```
> **证据**：`packages/react/src/utils/requestLock.ts:1-29`
> - `packages/js/src/ui/helpers/browser.ts:1-27`（SolidJS 版本）

**关键特性：**
- **原子性**：浏览器保证同一命名锁同一时间只有一个持有者
- **自动接管**：持锁标签页关闭/刷新时，锁自动释放，其他标签页立即竞争
- **按事件隔离**：每个 WebSocket 事件类型（RECEIVED/UNSEEN/UNREAD）有独立的锁

#### 11.4.2 BroadcastChannel：标签页间事件广播

**实现代码：`packages/react/src/hooks/internal/useBrowserTabsChannel.ts:1-36`**

```typescript
// 代码证据: useBrowserTabsChannel.ts 第1-36行
export const useBrowserTabsChannel = <T = unknown>({
  channelName,
  onMessage,
  enabled = true,
}: {
  channelName: string;
  onMessage: (args: T) => void;
  enabled?: boolean;
}) => {
  const [tabsChannel] = useState(
    typeof BroadcastChannel !== 'undefined' ? new BroadcastChannel(channelName) : undefined
  );

  // 发送消息给其他标签页
  const postMessage = (data: T) => {
    if (!enabled) return;
    tabsChannel?.postMessage(data);
  };

  useEffect(() => {
    if (!enabled) return;
    // 监听来自其他标签页的消息
    const listener = (event: MessageEvent<T>) => {
      onMessage(event.data);
    };
    tabsChannel?.addEventListener('message', listener);

    return () => {
      tabsChannel?.removeEventListener('message', listener);
    };
  }, [enabled]);

  return { postMessage };
};
```
> **证据**：`packages/react/src/hooks/internal/useBrowserTabsChannel.ts:1-36`
> - `packages/js/src/ui/helpers/useBrowserTabsChannel.ts:1-31`（SolidJS 版本）

**消息流向：**
```
[标签页A] (持有锁)
    │
    ├─ 接收 WebSocket 事件 (novu.on)
    │
    ├─ 本地处理 (onMessage)
    │
    └─ BroadcastChannel.postMessage()
           │
           ▼
    ┌───────────────────────────┐
    │ BroadcastChannel          │
    │ (同一浏览器内共享)         │
    └───────────────────────────┘
           │
           ├─────────────────────┐
           ▼                     ▼
    [标签页B]             [标签页C]
    (无锁)                 (无锁)
    onMessage()          onMessage()
```

### 11.5 多标签页场景下的断线恢复

| 标签页角色 | 断线恢复行为 | 代码证据 |
|-----------|-------------|----------|
| **首领标签页（持锁）** | Socket.IO/PartySocket 内置自动重连 → 重新获得锁 → 恢复事件订阅 | `socket.ts:183`, `requestLock.ts:15` |
| **追随者标签页（无锁）** | 不直接处理重连 → 通过 BroadcastChannel 接收首领广播的事件 | 无需代码，被动接收 |
| **首领切换时** | 原首领释放锁 → 新首领获得锁 → 新首领调用 `novu.on()` 订阅事件 | `useWebsocketEvent.ts:32-44` |

**首领切换场景示例：**
1. 用户关闭标签页 A（原首领）
2. 浏览器自动释放 Web Lock
3. 标签页 B 的 `navigator.locks.request` 获得锁
4. 标签页 B 执行回调：`novu.on(webSocketEvent, updateReadCount)`
5. 标签页 B 成为新首领，同时继续通过 BroadcastChannel 广播给其他标签页

### 14.2 多事件监听是否导致多次 connect 执行？

#### 14.2.1 场景分析：同时使用 useNotifications 和 useCounts

**使用场景（React Hooks）：**
```typescript
// 组件A: 使用 useNotifications
const { notifications } = useNotifications();

// 组件B: 使用 useCounts
const { counts } = useCounts({ filters: [{ read: false }] });
```

**实际调用链：**

| Hook | 监听的 WebSocket 事件 | 是否触发 connect() |
|------|----------------------|-------------------|
| `useNotifications` | `notifications.notification_received` | 是（第1次调用） |
| `useCounts` | `notifications.notification_received` | 是（#socketIo 存在，return） |
| `useCounts` | `notifications.unread_count_changed` | 是（#socketIo 存在，return） |

**实际连接次数：1 次（幂等保护生效）**

#### 14.2.2 并发连接出现的条件

**并发连接只可能在以下极端场景出现：**

| 场景 | 原因 | 代码证据 |
|------|------|----------|
| 1. 多标签页各获得不同事件锁 | 事件维度加锁，不同事件锁相互独立 | `useWebsocketEvent.ts:17` |
| 2. 同一标签页内多事件同时初始化 | `useEffect` 批量执行，首次调用时 `#socketIo` 尚未赋值 | `socket.ts:175` |
| 3. Session 初始化期间的竞态 | `callWithSession` 队列中的并发调用 | `base-module.ts:60-62` |

**场景1详细分析：事件维度加锁导致多连接**

```
标签页A                          标签页B
    │                                │
    ├─ useWebSocketEvent(RECEIVED)  │
    │   ├─ requestLock(RECEIVED)    │
    │   └─ 获得锁 → novu.on(RECEIVED)
    │                                │
    │                                ├─ useWebSocketEvent(UNSEEN)
    │                                │   ├─ requestLock(UNSEEN)
    │                                │   └─ 获得锁 → novu.on(UNSEEN)
    │                                │
    └─ 建立 WebSocket 连接           └─ 建立 WebSocket 连接
       （独立的Socket实例）             （独立的Socket实例）
```

**锁ID 包含事件类型，导致不同事件锁相互独立：**

```typescript
// 代码证据: useWebsocketEvent.ts 第17行
const channelName = `nv_ws_connection:a=${novu.applicationIdentifier}:s=${novu.subscriberId}:c=${novu.contextKey}:e=${webSocketEvent}`;
//                                                                                           ^^^ 每个事件有独立的锁
```
> **证据**：`packages/react/src/hooks/internal/useWebsocketEvent.ts:17`
> - SolidJS 版本相同：`packages/js/src/ui/helpers/useWebSocketEvent.ts:17`

**锁 ID 构成示例：**
- RECEIVED 事件锁：`nv_ws_connection:a=app123:s=sub456:c=:e=notifications.notification_received`
- UNSEEN 事件锁：`nv_ws_connection:a=app123:s=sub456:c=:e=notifications.unseen_count_changed`
- UNREAD 事件锁：`nv_ws_connection:a=app123:s=sub456:c=:e=notifications.unread_count_changed`

> **关键发现：3 个 Socket 事件对应 3 个独立的 Web Lock，可能导致同一浏览器内建立 3 个独立的 WebSocket 连接！**

### 14.3 监听释放后连接是否自动断开？

#### 14.3.1 答案：**不会自动断开**

**novu.on() 返回的 cleanup 函数只移除事件监听器，不影响连接状态：**

```typescript
// 代码证据: novu.ts 第109-119行
this.on = (eventName, listener) => {
  if (this.socket.isSocketEvent(eventName)) {
    this.socket.connect();  // 自动建连
  }

  const cleanup = this.#emitter.on(eventName, listener);

  return () => {
    cleanup();  // ⚠️ 只调用 emitter.off()，不调用 socket.disconnect()
  };
};
```
> **证据**：`packages/js/src/novu.ts:116-118`

**mitt 事件发射器的 off() 只移除监听器，不管理连接：**

```typescript
// 代码证据: novu-event-emitter.ts 第19-21行
off<Key extends EventNames>(eventName: Key, listener: EventHandler<Events[Key]>): void {
  this.#mittEmitter.off(eventName, listener);  // 只从 mitt 的 Map 中移除
}
```
> **证据**：`packages/js/src/event-emitter/novu-event-emitter.ts:19-21`

#### 14.3.2 连接关闭的责任归属

| 关闭场景 | 责任方 | 触发方式 | 代码证据 |
|---------|--------|----------|----------|
| **正常关闭** | 接入方 | 显式调用 `novu.socket.disconnect()` | `socket.ts:239-245` |
| **页面关闭** | 浏览器 | WebSocket 自动断开 | 浏览器行为 |
| **网络超时** | Socket 库 | 心跳超时检测 | `socket.io-client` 内置 |
| **Tab 休眠恢复** | 重连机制 | 自动重连 | `socket.ts:183` |
| **订阅者切换** | SDK 内部 | `changeSubscriber()` 中调用 | `novu.ts:149-150` |

**唯一的内部断开场景：切换订阅者**

```typescript
// 代码证据: novu.ts 第149-150行
// Disconnect and reconnect socket to use new JWT token
const disconnectResult = await this.socket.disconnect();
```
> **证据**：`packages/js/src/novu.ts:149-150`

### 14.4 React vs SolidJS 实现的时序分析

#### 14.4.1 React 版本时序（可复现）

**场景：单标签页同时渲染 useNotifications 和 useCounts**

```
时间轴 (t)   操作                                      连接状态
──────────  ───────────────────────────────────────  ─────────
t0          React 批量调度 effects                    未连接
            ├─ useNotifications useEffect
            └─ useCounts useEffect
            │
t1          useNotifications effect 执行
            ├─ requestLock(RECEIVED)
            ├─ 获得锁
            ├─ novu.on(RECEIVED, handler)
            │   ├─ isSocketEvent(RECEIVED) → true
            │   └─ socket.connect()
            │       ├─ #socketIo 不存在 → #initializeSocket()
            │       ├─ emit('socket.connect.pending')
            │       └─ 创建 Socket.IO 实例（异步连接）
            │
t2          useCounts effect 执行
            ├─ requestLock(RECEIVED)
            │   └─ 锁已被持有 → 等待
            ├─ requestLock(UNREAD)
            │   └─ 获得锁
            └─ novu.on(UNREAD, handler)
                ├─ isSocketEvent(UNREAD) → true
                └─ socket.connect()
                    └─ #socketIo 已存在 → return（幂等）
            │
t3          Socket.IO 连接建立成功
            ├─ socket.on('connect') 触发
            └─ emit('socket.connect.resolved')
            │
t4          新通知到达服务端
            ├─ 服务端通过 WebSocket 推送 RECEIVED 事件
            └─ Socket.IO 接收事件 → 分发给所有绑定的处理器
            │
t5          组件卸载
            ├─ useNotifications cleanup 执行
            │   ├─ cleanup() → emitter.off(RECEIVED, handler)
            │   └─ resolveLock() → 释放 RECEIVED 锁
            └─ useCounts cleanup 执行
                ├─ cleanup() → emitter.off(RECEIVED, handler)
                ├─ cleanup() → emitter.off(UNREAD, handler)
                ├─ resolveLock() → 释放 UNREAD 锁
                └─ ⚠️ WebSocket 连接 **仍然保持**
```

```
t0         mount → useEffect                     mount → useEffect
```

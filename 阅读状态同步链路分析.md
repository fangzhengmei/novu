# 用户阅读状态同步链路分析

## 一、整体架构概览

用户阅读状态（已读/已见/归档等）的同步是一个跨多终端、多服务的完整链路。系统采用 **"HTTP上报 + WebSocket广播 + 数据库持久化 + 最终一致性补齐"** 的架构模式。

#### 1.1 状态上报机制 (`src/notifications/helpers.ts`)

**核心逻辑：乐观更新 + 事件驱动**

```typescript
// 单个通知标记为已读
export const read = async ({ emitter, apiService, args }) => {
  // 1. 生成乐观更新值
  const optimisticValue = new Notification({ ...notification, isRead: true, readAt: now });
  
  // 2. 发射 pending 事件，UI 立即响应
  emitter.emit('notification.read.pending', { data: optimisticValue });
  
  try {
    // 3. 异步调用后端 API
    const response = await apiService.read(notificationId);
    
    // 4. 发射 resolved 事件，更新最终状态
    emitter.emit('notification.read.resolved', { data: updatedNotification });
  } catch (error) {
    // 5. 失败时回滚
    emitter.emit('notification.read.resolved', { error });
  }
};
```

**上报 API 接口：**

| 操作 | HTTP 方法 | 路径 | 说明 |
|------|----------|------|------|
| 标记单个已读 | PATCH | `/inbox/notifications/:id/read` | 单个通知 |
| 标记单个未读 | PATCH | `/inbox/notifications/:id/unread` | 单个通知 |
| 批量标记已见 | POST | `/inbox/notifications/seen` | 支持按 ID 或筛选条件 |
| 批量标记已读 | POST | `/inbox/notifications/read` | 支持按标签/数据筛选 |
| 批量归档 | POST | `/inbox/notifications/archive` | 支持按条件批量 |

#### 1.2 WebSocket 实时监听 (`src/ws/socket.ts`)

**连接管理：**
- 使用 `socket.io-client` 建立长连接
- 自动重连：`reconnectionDelayMax: 10000`
- 认证方式：URL Query 参数携带 JWT Token

**监听的实时事件：**

| 事件名 | 触发时机 | 数据结构 |
|--------|----------|----------|
| `notification_received` | 收到新通知 | `{ message: InboxNotification }` |
| `unseen_count_changed` | 未见计数变化 | `{ unseenCount: number, hasMore: boolean }` |
| `unread_count_changed` | 未读计数变化 | `{ unreadCount: number, counts: { total, severity }, hasMore }` |

#### 1.3 本地缓存与事件同步 (`src/cache/notifications-cache.ts`)

**缓存键设计：**
- 基于查询参数（tags、read、archived、severity 等）生成 JSON 字符串作为键
- 自动监听状态变更事件，更新缓存中的通知状态

**监听的更新事件：**

##### 2.2.1 标记通知为已见 (`mark-notifications-as-seen.usecase.ts:1-280`)

**执行流程：**
1. 校验订阅者存在性
2. 按 ID 或筛选条件批量更新数据库
3. 记录交互轨迹（ClickHouse）
4. 失效缓存
5. 发送 WebSocket 队列任务广播计数变化

**关键代码片段：**
```typescript
async execute(command: MarkNotificationsAsSeenCommand): Promise<void> {
  // 1. 批量更新数据库（分批处理，每批50条）
  const BATCH_SIZE = 50;
  for (const idChunk of notificationIdChunks) {
    const batchResults = await this.messageRepository.updateMessagesStatusByIds({
      environmentId, subscriberId, ids: idChunk, seen: true,
    });
    updatedMessages.push(...batchResults);
  }

  // 2. 失效计数缓存
  await this.invalidateCache.invalidateQuery({

  this.webSocketsQueueService.add({
    name: 'sendMessage',
    data: {
      event: WebSocketEventEnum.UNSEEN,
      userId: subscriber._id,
      _environmentId,
      contextKeys,
    },
    groupId: subscriber._organizationId,
  });
}
```

#### 3.2 核心更新方法

##### `updateMessagesStatusByIds` (第751行)

按通知 ID 列表批量更新状态：

```typescript
async updateMessagesStatusByIds({
  environmentId, subscriberId, ids, seen, read, archived, snoozedUntil, contextKeys
}): Promise<MessageEntity[]> {
  const query = {
    _environmentId: environmentId,
    _subscriberId: subscriberId,
    _id: { $in: ids.map(id => new Types.ObjectId(id)) },
    ...(contextKeys?.length && { contextKeys: { $in: contextKeys } }),
  };
  
  return this.updateMessagesStatus({ query, seen, read, archived, snoozedUntil });
}
```

##### `updateMessagesFromToStatus` (第790行)

按筛选条件批量更新：

```typescript
async updateMessagesFromToStatus({
  environmentId, subscriberId, from, to, contextKeys
}): Promise<MessageEntity[]> {
  // from: 筛选条件（tags, data, seen, read, archived）
  // to: 目标状态
  let query = {
    _environmentId, _subscriberId,
    ...(contextKeys?.length && { contextKeys: { $in: contextKeys } }),
    ...from.tagGroups && buildTagsQuery(from.tagGroups),
    ...from.data && getFlatObject({ data: from.data }),
  };
  
  return this.updateMessagesStatus({ query, ...to });
}
```

### 4. WebSocket 服务层 (`apps/ws`)

#### 4.1 网关层 (`socket/ws.gateway.ts:1-379`)

**核心职责：**
- 管理 WebSocket 连接生命周期
- 处理连接认证（JWT 校验）
- 按订阅者分组（Socket.IO rooms）
- 向在线客户端推送实时事件

**连接建立流程：**
```
客户端连接
    ↓
extractToken() - 从 handshake 提取 token
    ↓
getSubscriber() - JWT 校验，确认身份
    ↓
connection.join(subscriber._id) - 加入订阅者房间
    ↓
subscriberOnlineService.handleConnection() - 更新在线状态
```

**上下文隔离机制：**
每个连接携带 `contextKeys`，广播时进行精确匹配，确保多上下文场景下的数据隔离。

```typescript
private isExactMatch(messageContextKeys: string[], inboxContextKeys: string[]): boolean {
  if (messageContextKeys.length === 0) return inboxContextKeys.length === 0;
  if (messageContextKeys.length !== inboxContextKeys.length) return false;
  return messageContextKeys.every(key => inboxContextKeys.includes(key));
}
```

#### 4.2 事件路由 (`usecases/external-services-route/external-services-route.usecase.ts:1-157`)

根据事件类型执行不同的广播逻辑：

| 事件类型 | 处理逻辑 |
|----------|----------|
| `RECEIVED` | 推送完整通知内容 + 同步更新 unseen/unread 计数 |
| `UNSEEN` | 重新查询数据库，推送最新未见计数 |
| `UNREAD` | 重新查询数据库，推送最新未读计数（含严重程度分组） |

#### 4.3 在线状态管理 (`shared/subscriber-online/subscriber-online.service.ts:1-39`)

维护订阅者的在线状态：
```typescript
async handleConnection(subscriber) {
```

```typescript
private getWorkerProcessor() {
  return async (job) => {
    const data: IWebSocketDataDto = job.data;
    
    await this.externalServicesRoute.execute(
      ExternalServicesRouteCommand.create({
        userId: data.userId,
        event: data.event,
        payload: data.payload,
        _environmentId: data._environmentId,
        contextKeys: data.contextKeys,
      })
    );
  };
```

**重要设计决策：**
> WS 任务采用 **at-most-once** 语义，失败不重试。因为 WS 消息是实时 UI 提示，过期后重播反而有害。客户端可通过主动拉取来修复状态。

## 四、关键设计决策与技术要点

### 1. 状态模型设计

**Seen vs Read 的区别：**
- **Seen（已见）**：通知出现在用户视野中，自动标记
- **Read（已读）**：用户主动点击查看，需要显式操作

**状态联动规则：**
- 标记为已读 → 自动标记为已见
- 标记为已归档 → 自动标记为已读+已见
- 标记为未见 → 自动取消已读+已归档

### 2. 多终端同步策略

**最终一致性保障：**
1. **实时通道**：WebSocket 推送计数变更事件（秒级）
2. **数据库基准**：HTTP API 拉取确保数据准确（用户主动刷新时）
3. **缓存失效**：状态变更后立即失效服务端缓存
4. **幂等操作**：重复标记同一状态不会产生副作用

### 3. 断线重连补齐机制

系统 **没有** 采用"事件溯源 + 离线消息队列"的复杂方案，而是采用更简洁的最终一致性策略：

1. **WebSocket 自动重连**：socket.io 内置重连机制，指数退避
2. **重连后主动拉取**：应用层监听 `connect` 事件，触发全量数据刷新
3. **计数基准对齐**：每次 WebSocket 推送的是数据库实时查询结果，不是增量事件
4. **本地缓存自愈**：客户端缓存监听所有状态事件，自动合并更新

**设计考量：**
- 避免维护复杂的离线消息队列和 ack 机制
- 计数推送是幂等的，重复推送不影响正确性
- 用户感知不到短暂的不一致（秒级内自愈）

### 4. Context Keys 隔离机制

支持同一订阅者在不同上下文（如不同租户、不同项目）下的状态隔离：
- 连接时携带 `contextKeys`
- 状态更新时指定 `contextKeys` 筛选条件
- WebSocket 广播时进行精确匹配
- 数据库查询时加入 `contextKeys` 过滤

### 5. 性能优化点

| 优化手段 | 实现位置 | 效果 |
|---------|----------|------|
| 批量更新分批处理 | `message.repository.ts` | 避免单次更新过多文档 |
| 乐观更新 | `packages/js/src/notifications/helpers.ts` | UI 无延迟响应 |
| 本地缓存 | `notifications-cache.ts` | 减少重复网络请求 |
| 服务端缓存 | `invalidate-cache.service.ts` | 加速计数查询 |
| 异步广播 | `web-sockets-queue.service.ts` | 解耦 HTTP 请求与 WS 推送 |
| 上下文匹配 | `ws.gateway.ts` | 避免不必要的消息发送 |
| 计数分页指示 | `getCount()` | 超过100条时返回 hasMore，避免全表扫描 |

## 六、总结

### 架构优点
1. **职责清晰**：各层边界明确，单一职责原则贯彻良好
2. **高内聚低耦合**：通过事件总线和队列解耦各模块
3. **用户体验优先**：乐观更新确保 UI 响应迅速
4. **可扩展性**：Use Case 模式便于新增操作类型
5. **可靠性**：数据库持久化 + 最终一致性确保数据不丢

### 关键设计模式
- **命令模式**：Use Case + Command 封装业务操作
- **观察者模式**：Event Emitter 实现模块间通信
- **仓库模式**：Repository 封装数据访问
- **乐观并发**：客户端乐观更新 + 服务端最终覆盖
- **异步队列**：解耦同步请求与异步广播
